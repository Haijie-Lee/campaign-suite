# ID 体系规范

> 最后更新：2026-09-23
>
> 本规范为 trans-forge 转化产物的 ID 用法纪律，与 `campaign/tools/doc_graph.md` 的 K3 schema / ID 词法保持一致。

## 一、前缀白名单

允许作为需求/决策/风险/验收等注册表 ID 前缀的仅有以下 7 个：

| 前缀 | 含义 | 登记位置 |
|---|---|---|
| FR | 功能需求（Functional Requirement） | §3.2 功能需求表 |
| NFR | 非功能需求（Non-Functional Requirement） | §3.3 非功能需求表 |
| C | 已确认决策（Confirmed Decision） | §0.4 已确认决策注册表 |
| D | 待决策事项（Decision） | §10 待决策事项注册表 |
| Q | 需求澄清与假设（Question） | §3.4 需求澄清与假设注册表 |
| R | 风险（Risk） | §9 风险与对策 |
| AC | 验收标准（Acceptance Criteria） | §8.3 验收标准 |

**禁单字母 `P` 作前缀**。案例实证：flow-builder spec 中问题清单前缀 `P`（P1–P14）与 `P0`（优先级）、`P95`（NFR 分位数）、`P256`（ECDSA 曲线）发生正则互污染，导致机器解析歧义。

## 二、稳定编号纪律

需求条目一经发布，编号只增不改：

- FR/NFR/R/D/C/Q/AC 一经定义，**不删除、不改号**。
- 新增条目接续最大编号；废弃条目标记 `deprecated`，保留编号以避免既有引用断裂。
- 若发现内容重复（如 FR-8.8 与 FR-7.7 同指一改造），应合并语义并对其中一条标记 deprecated，而非改号。

## 三、引用形态

### 3.1 正文引用

正文禁止使用通配引用，例如 `FR-3.x`、`NFR-5.x`。如需指代整组，使用注记形态：

```markdown
FR-3 全组
NFR-2 全组
```

### 3.2 区间引用

区间引用（如 `FR-2.1–2.4`）**仅允许出现于索引区、锚点区**，不得在正文章节内泛化使用（含映射表——映射设计表逐行列目标节、不用区间引用压缩）。正文中应逐条引用或改用组注记。

## 四、TODO token 语法

TODO 标记统一使用 `TODO-<主题>:` 形态，并遵守以下纪律：

- **一处值一 token**：每个 TODO 只对应一个待确认主题。正例：`TODO-上传上限:`、`TODO-会话上限:`。（`TODO-推理线程:`/`TODO-推理内存:` 不作正例——见下条反例。）
- **禁斜杠复合**：禁止 `TODO-端口段/TODO-网络分段` 这种一个 token 内嵌两个主题的形式。
- **禁同义异名**：同一待确认值只能有一个 TODO 主题。反例：flow-builder 中 `TODO-推理线程` 与 `TODO-推理内存` 同指一值，造成重复登记。
- 行内 TODO 不单独占 D 号；§10/DECISIONS.md 为唯一集中登记点。

## 五、doc_graph 已知限制

`campaign/tools/doc_graph.md` 已知限制节登记（词法 v1.2 候选，2026-09-21 登记）：组 ID（FR-8/9/10 等无子号的裸组号）在叙事性加粗提及（如文档头修订叙事 `**FR-9 链路体检…**`、C 决策表行内加粗）处被规则②判为定义，与组标题定义双重计数 → `duplicates` 假阳性。该误报为已知限制，非文档缺陷；收编时应人工复核 duplicates 列表，剔除裸组号的叙事性加粗误报。
