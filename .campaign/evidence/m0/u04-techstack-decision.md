## 2. 数据对 SRS 论断的验证

| SRS §4.3 论断 | 实测结论 |
|---|---|
| 「吞吐本身不是 Python 的硬伤，瓶颈通常在网络与磁盘」（§4.3.4） | **成立**：双栈吞吐（2043 / 1372 MB/s）均超产品需求两个数量级（NFR-2.1 目标 ≈ 上行 100 Mbps × 85% ≈ 10.6 MB/s）。吞吐不构成决策区分度 |
| 「BLAKE3 与传输并行时 Python 会与事件循环争抢 CPU」（§4.3.4） | 未直接验证（单线程基准）；Python 吞吐方差更大（1018–1494，振幅 47%）vs Rust（1796–2066，振幅 15%）——与「Python 长稳性需额外调优」同向，但单次基准不足以定论，留 M1 长跑压测 |
| 「常驻内存恒定是硬要求，Rust 天然满足」（§4.3.4，NFR-2.3 < 300 MB） | **同向**：Rust 基线 13 MB vs Python 33 MB（≈2.5×）。双达 300 MB 门槛，但 Python 基线含解释器固有成本，叠加 WebView 与传输缓冲后余量更薄 |
| 「Python 的真正痛点在分发形态与杀软误报」（§4.3.3） | 本会话不可测（需打包 + 签名 + 杀软环境）——挂起，不推翻 SRS 分析 |

## 3. 决策与依据

**确认主选 Rust + Tauri 2**（SRS §4.3.5 推荐 + 实测未推翻）：

1. 吞吐双达且远超需求——决策区分度落在分发形态、内存基线、权限模型、杀软误报四项，均为 Rust 优势面（SRS §4.3.3/4.3.5 分析未被实测推翻）；
2. 传输引擎本需原生能力（分片/seek/fsync/并发 IO），Tauri Rust 侧正好承载；
3. Go + Wails 备选保留（云端即 Go、代码可复用是实益），但桌面生态成熟度略逊，且无推翻主选的新证据。

**⚠️ 开发规范硬条目（SRS §4.3.5 留坑，随决策生效）**：Tauri `dragDropEnabled: true`（默认）在 Windows 拦截 HTML5 拖放——前端必须用 Tauri 原生拖拽事件 API（`onDragDropEvent`），禁依赖 `drop` + `DataTransfer`。
